# Rollover (Phase 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A finished night stops being dropped and becomes an archived NightRecord — whether the app was closed across the boundary or left open through it.

**Architecture:** `storage.js` grows one exported function, `archived`, which folds a blob's logs into the front of its archive; `forNight` calls it instead of discarding. `App.jsx` gains a `nightRef` holding the current night ID, an `archive` state array, and a third effect that adopts a re-labelled night without folding it. The write effect stops re-deriving its stamp from the wall clock and reads the ref, which is what stops a log tapped just after the boundary from dragging the whole previous night across it.

**Tech Stack:** Plain ES modules, React 18, Vitest 2, `localStorage`. No new dependencies.

## Global Constraints

- **No new dependencies.** No `jsdom`, no fake-timer library, no state library.
- **One key.** `"gy.v1"`, now holding `{ night, profile, logs, reflection, theme, archive }`. Not a second key for the archive.
- **Do not change `foldNight`'s signature or body.** It stays `foldNight(profile, logs, reflection)` in `stats.js`, and its `id: "tonight"` / `dayOffset: 0` are corrected at the archive site.
- **Do not touch `generateTimeline`, `materializeNights`, or the `history` useMemo.** `history` stays `[tonight, ...mock]` until Phase 3.
- **`dayOffset` is never stored.** It is relative to tonight; a stored one is wrong by morning.
- **The archive is newest-first.** Index 0 is the night most recently folded, matching the order every range slice already assumes.
- **The log shape does not change.** `t` stays axis-minutes.
- **Vitest runs in `environment: "node"`** (`vitest.config.js`). There is no `localStorage` and no DOM. Do not stub either.
- Spec: `docs/superpowers/specs/2026-08-12-rollover-design.md`.
- Test command: `npm test` (`vitest run`). Single file: `npx vitest run src/storage.test.js`.
- Line numbers below are from commit `c654ca5`. Match on code, not on the number.

### Task 1: `archived`, and `forNight` folding instead of dropping

**Files:**
- Modify: `src/storage.js`
- Test: `src/storage.test.js`

**Interfaces:**
- Consumes: `foldNight(profile, logs, reflection) -> NightRecord | null` from `src/stats.js`. Returns `null` when `logs` is empty. Its record includes `id: "tonight"` and `dayOffset: 0`, both wrong for a stored record.
- Produces:
  - `archived(s: object) -> NightRecord[]` — `s.archive` with `s`'s own night folded onto the front, or `s.archive` unchanged when there is nothing to fold. Never returns `undefined`.
  - `forNight(s, id)` — unchanged when `s.night === id`; otherwise now `{ profile, theme, archive: archived(s) }`.

**Background the implementer needs:**

`forNight` currently throws last night's logs away. `foldNight` in `stats.js` already turns exactly that data into a NightRecord — the same shape `mockNights.js` produces for its 45 authored nights — and is already covered by `stats.test.js`. Nothing has ever called it with a *previous* night's logs, because until Phase 1 there were none.

Two fields on that record are written for its existing caller and wrong for a stored one:

- `id: "tonight"` — every archived record would share it. It becomes the blob's `night` stamp, which is unique and stable.
- `dayOffset: 0` — this is relative to tonight, so it is wrong by morning. Worse, `Dashboard.jsx:179` finds a night with `nights.find((x) => x.dayOffset === off)`, so a stored `0` would make every archived night answer to the strip's "Today" chip. Drop the field; Phase 3 computes it from the `id`.

Correct them at the archive site rather than by growing `foldNight`'s signature — it has a second caller (the live `history` useMemo) that wants exactly what it returns today, and a mock counterpart that must keep matching it.

**Why `archived` is exported.** It has two callers: `forNight` here, and Task 2's tick. The alternative is the tick reconstructing a blob to hand to `forNight`, which is the same code arranged worse.

**Why a night with no logs archives nothing.** `foldNight` returns `null` for that, so it costs zero lines. The alternative — walking every date since the last stamp and writing `{id, empty: true}` stubs — buys an explicit off-night marker at the price of date arithmetic and a stretch rule committed to before there is an archive to test it against. Every record carries its night ID, so a gap in the sequence is visible to anything that looks, and Phase 5 decides what a gap means once it has data.

```js
/** Last night folded onto the front of the archive, newest first, which is the
    order every range slice in the app already assumes.
    dayOffset is dropped rather than stored: it is relative to tonight, so a
    stored one is wrong by morning and Dashboard.jsx would match every archived
    night against the strip's "Today" chip. Phase 3 computes it from the id.
    No night stamp means nothing to name the record; no logs means nothing to
    record. Both leave the archive alone, and the gap in the id sequence is the
    only trace an unworked night gets. */
export const archived = (s) => {
  const rec = s.night ? foldNight(s.profile, s.logs ?? [], s.reflection ?? {}) : null;
  if (!rec) return s.archive ?? [];
  const { dayOffset, ...night } = rec;
  return [{ ...night, id: s.night }, ...(s.archive ?? [])];
};

/** Last night's blob keeps the profile, the theme, and an archive one night
    longer; tonight's keeps everything. */
const forNight = (s, id) =>
  s.night === id ? s : { profile: s.profile, theme: s.theme, archive: archived(s) };
```

Leave the `export { load, save, forNight };` line at the bottom as it is — `archived` is exported inline, at its declaration, because it is the one thing here another module reaches for by name.

### Task 2: The app notices the night ending while it is open

**Files:**
- Modify: `src/App.jsx` — the import at line 17, the boot comment and constant at 2286–2307, two `useState`/`useRef` additions after line 2321, and the effect block at 2339–2357.

**Interfaces:**
- Consumes: `archived(s) -> NightRecord[]` from Task 1. `nightOf(ph, d = new Date()) -> { id, now }` from `src/time.js`; `id` is the `"YYYY-MM-DD"` name of the night and `now` is the plan-axis position, both from one call. `calculateShiftPhases(profile) -> ph`. `say(msg)` at `App.jsx:2391` shows a toast for 2.6s.
- Produces: nothing importable. The observable contract is that a night which ends is in `gy.v1`'s `archive`, and that the logs of the night in progress are not.

**Background the implementer needs:**

**The bug this closes is not the drop; it is the write.** `App.jsx:2343` re-derives the night stamp from the wall clock on every save. The tick moves `now` onto the new night's axis on its own 30-second clock, but the write effect does not depend on `now` — it fires on the next change to `logs`, and writes the *entire accumulated log set*, last night's and tonight's together, under the new night ID. On the next reload `forNight` sees that ID match and keeps all of it. Every night after is "tonight" until the app is closed and reopened. Phase 1 named this as its worst ceiling.

**The trap that is not in the spec's problem statement, and that you must not skip.** `nightOf` reads the wake boundary out of the profile, and the sheet at `App.jsx:2685` lets the user edit `shiftStart`, `shiftEnd`, `plannedSleep` and `sleepGoalHours` live, mid-night, promising only that "changing this rebuilds tonight's plan around the new times." Any of those edits can change which night the current clock belongs to. To a naive rollover check that is indistinguishable from a boundary crossing — so editing your shift time at 3am would archive the night you are standing in and clear the plan under you.

The fix is a third effect that **adopts** the new ID without folding, declared *above* the other two so that React, which runs effects in declaration order, corrects the ref before anything reads it. It also removes any need to seed the ref from `finishQuiz`: the profile goes from `null` to a real one, the adopt effect fires on that, and the first tick after onboarding sees a match instead of rolling a night that never happened.

The invariant, worth holding in your head for the whole task: **`nightRef.current` equals `nightOf(profile).id` at all times except between a boundary crossing and the tick that answers it.** The adopt effect holds one half, the tick holds the other, and nothing else writes to the ref.

**Why `archive` is state and `nightRef` is a ref.** Nothing renders the night ID — only these effects read it — which is the same reason Phase 1 declined to put it in state. The archive is different: the write effect must fire when it grows. It would in fact be flushed anyway, because the roll sets `logs` in the same batch and `logs` is already a dependency of the write — which is exactly the kind of load-bearing coincidence that costs an hour to re-derive later.

- [ ] **Step 4: Replace the effect block**

`src/App.jsx:2339-2357` — the write effect with its comment, and the tick effect. Replace both, in full, with three effects in this order:

```js
  /* nightOf reads the wake boundary out of the profile, so editing your shift
     or sleep times can change which night the current clock belongs to. That is
     a re-labelling, not a rollover: adopt the new id without folding. Without
     this, changing your shift time at 3am looks exactly like a boundary
     crossing to the tick below, which would archive the night you are standing
     in and clear the plan under you. It covers the quiz too — profile goes null
     to set, this fires, and the first tick sees a match rather than rolling a
     night that never happened. Declared first on purpose: effects run in order,
     so the ref is correct before anything below reads it. */
  useEffect(() => {
    if (profile) nightRef.current = nightOf(calculateShiftPhases(profile)).id;
  }, [profile && profile.shiftStart, profile && profile.shiftEnd,
      profile && profile.plannedSleep, profile && profile.sleepGoalHours]);

  /* One key, one blob, one write. The stamp comes off the ref rather than the
     clock: between the boundary and the tick that answers it, the logs in hand
     are still last night's and have to be written under last night's name.
     Deriving it here from the clock is what let a single log tapped in that
     window carry a whole night across the boundary. The guard also means
     nothing reaches the device until the quiz is finished. */
  useEffect(() => {
    if (!profile) return;
    save({ night: nightRef.current, profile, logs, reflection, theme: themeOverride, archive });
  }, [profile, logs, reflection, themeOverride, archive]);

  useEffect(() => {
    if (!profile) return;
    const tick = () => {
      const { id: night, now } = nightOf(calculateShiftPhases(profile));
      setNow(now);
      if (night === nightRef.current) return;
      /* the night ended while the app was open: fold it, then start clean */
      const next = archived({ night: nightRef.current, profile, logs, reflection, archive });
      nightRef.current = night;
      setArchive(next);
      setLogs([]);
      setReflection({});
      /* only when something was actually folded — "last night is saved" is a
         lie for a night with nothing logged, and nothing visibly unticks */
      if (next.length > archive.length) say("Last night is saved. Tonight's plan starts fresh.");
    };
    tick();
    const id = setInterval(tick, 30000);
    return () => clearInterval(id);
  }, [profile, logs, reflection, archive]);
```

Three details that are easy to get wrong:

- The night ID is destructured as `night`, not `id`, because `id` is already the interval handle two lines below it. Shadowing it compiles and reads terribly.
- **The tick's dependency list collapses; the adopt effect's does not, and the asymmetry is deliberate.** The tick reads `[profile && profile.shiftStart, ...]` today to avoid rebuilding the interval on unrelated profile changes. Since `logs`, `reflection` and `archive` now have to be in there — the roll reads all three — it rebuilds on every log tap anyway, so the field list has stopped optimising anything and `profile` whole is one term instead of four. Do **not** apply the same collapse to the adopt effect above: it would widen the window in the next bullet from "edited a shift time" to "touched anything on the profile", because adjusting a planning parameter writes a new `profile` object. The tick never adopts, so re-running it costs an interval rebuild and nothing else.
- **A profile edit within 30 seconds of a real boundary swallows that rollover.** The adopt effect moves the ref, the tick then sees a match, and the write stamps the merged logs under the new ID so the next boot does not catch it either. Accepted: the alternative is a mis-detected roll archiving a live night and wiping the plan. Do not add a guard for it.
- The interval restarting on each log tap is fine for the case this exists for. When the app sits idle across the boundary no render happens, the effect does not re-run, and the closure holds the logs that were current when the night ended.

## Explicitly not in this plan

- Reading the archive into `history`, demoting the mock to a dev seed, or any empty state (Phase 3).
- Off-night stubs, a nights-elapsed counter, or `nightInStretch` counting itself (Phase 5).
- Archiving plan item lists so a past night's Plan page can be re-read. The roadmap recommends against it: history is a summary.
- A profile snapshot per archived record. A record is folded against the *current* profile, so changing your shift times shifts a stored night's `cutoff` and `moveTotal` — a named ceiling, and it distorts nothing anything reads yet.
- Retention limits or compaction. ~250 bytes a night is ~90KB a year against localStorage's ~5MB.
- A `storage` event listener. Two tabs crossing the boundary can each fold the same night; that is the Phase 1 multi-tab ceiling with a duplicate record as its new symptom.
- Any test of the tick. It is a React effect over an interval and a wall clock, so asserting on it means a render harness and fake timers — a larger addition than the phase. The fold it calls is the part with logic, and Task 1 covers it.
- Persisting `tab`, `hideDone`, `showAllPlan` or `rangeKey` (Phase 4).
